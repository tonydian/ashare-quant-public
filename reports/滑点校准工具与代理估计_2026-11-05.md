> ｜ 模板 `journal/fills/fills_2026-11-06.csv`

> **一句话结论：40bp 里「必须付」的只有约 8bp（半价差），剩下 32bp 是在给「不可能正好按开盘价成交」买保险。所以 40bp 大概率偏高，真值更可能在 15~25bp —— 但那要等实测，日线给不出。**

## 0. 这个数为什么值钱

`qf/config.py::SLIPPAGE_BP = 40`，`build/exp_slippage.py` 开头自己写着
「**这个数是拍的，没有任何成交数据支撑**」。

它在成本里占 **79.3%**：单笔 50.45bp 中 40bp 是滑点。年化口径 =
`单笔 50.45bp × 年双边换手 1.514 = 0.764%`，其中滑点 0.605pp。

对照：因子层三条路跑完最好的一档是 **+0.16pp**，还判否了。
**把 40bp 校准到真值，量级比过去两周所有因子工作加起来都大。**

## 1. 日线能给出什么、给不出什么

**给不出**：真实滑点需要盘口（买卖价差、队列深度）和成交明细，项目里都没有。

**能给**：两个物理量级，用来判断 40bp 是不是离谱：

| 量 | 数值 | 含义 |
|---|---:|---|
| 1 tick（0.01 元）折算 | 中位 **16.82bp** | 现值越高、tick 占比越小 |
| 40bp 折合几个 tick | **2.38 个** | 认为每笔要付 2 个多价位 |
| 半价差（价差 = 1 tick 假设） | **8.4bp** | 这是「必须付」的下界 |
| 日内振幅（high−low）/中价 | 中位 **219.4bp** | 一天的价格活动范围 |
| 开盘→收盘 漂移 | 中位 −10.48bp，均值 −5.91bp，σ 183bp | |
| &#124;开盘→收盘&#124; | 中位 **92.88bp**，75 分位 168bp | |
| 开盘后 30 分钟典型漂移（×√(30/240)） | **32.8bp** | 「坚持开盘价成交」要承担的量级 |

样本：当前 40 只持仓 × 最近 120 个交易日（4,779 个股票-日）。
后复权同空间计算（`amount/volume` 是原始价、`close` 是后复权价，两者不可直接比 —— 这里踩过一次）。

### 41 ≈ 40 是个巧合，不是验证

```
半价差 8.4bp  +  开盘后 30 分钟漂移 32.8bp  =  41.2bp  ≈  配置 40bp
```

看起来很漂亮，但**加法不成立**：

- 8.4bp 是**必然成本**（你总得跨过价差）
- 32.8bp 是**零均值的价格位移**，不是成本。它衡量的是"如果你被迫在开盘后一段时间内
  随机成交，成交价相对开盘价跑多远"，长期期望是 0，只有当你有系统性信息劣势时才变成成本。

所以正确的读法是：**40bp 是一个留了 4 倍缓冲的上界**，
真值 = 半价差（8bp）+ 一点成交劣化（小单冲击 <0.1bp）+ 佣金退化项。

### 顺手发现：佣金不是 1bp

`C.COMMISSION_BP = 1`，但有 **最低 5 元**。单笔均额 7,067 元 → `5 / 7067 = 7.08bp`。
拆开对账：

| 项 | 预估 | 说明 |
|---|---:|---|
| 滑点 | 40.0bp | 假设值 |
| 佣金 | **7.1bp** | 1bp 被 5 元下限顶成 7.1bp |
| 印花税 | 2.5bp | 5bp，仅卖出，按买卖各半摊 |
| 过户费 | 0.1bp | |
| **合计** | **49.7bp** | 实测 `cost_bp_per_trade` = **50.45bp** ✓ |

对得上。**小资金下佣金已经是滑点的 18%，不是 2.5%。** 这条以前没单独说过。

### 一个不值得做的发现

开盘→收盘均值 **−5.91bp**（收盘价低于开盘价）。若把成交从"次日开盘"推迟到"次日收盘"，
买入平均便宜 5.91bp，年化收益 **+0.089pp**。

不值得：一是量级太小（换来的是一整天的价格暴露），二是这个均值只有 t ≈ 2.2、
且样本重叠严重。记录在此，不建议实施。

## 2. 工具：从今天起开始攒数据

### 三步

```bash
python scripts/fill_log.py new                    # 每个调仓日跑一次，生成待填模板
# 手工填 filled_px / filled_shares 两列（只填实际成交的）
python scripts/fill_log.py report                 # 攒够 20 笔后跑
python scripts/fill_log.py proxy                  # 随时可跑，就是本文第 1 节
```

### 已经生成的模板

`journal/fills/fills_2026-11-06.csv` —— **60 笔**（50 只股票 + 10 只转债），
列：`signal_date, trade_date, code, name, kind, side, plan_shares, unit, ref_close, open_px, filled_px, filled_shares, note`。

`ref_close` 和 `plan_shares` 直接从 `signals/latest_combo.json` 取，
**已经换算到真实可下单价格空间**（行情面板是后复权价，直接比会出现"模板 51.44、实际 5.32"这种没法核对的情况——这是实现时踩的坑，已用测试钉住）。

`open_px` 在交易日过后可以自动补：`python scripts/fill_log.py new --date 2026-11-06 --force`。

### 口径（写死在代码和测试里）

- **滑点，正数 = 吃亏**
  - 买入 `(成交价 / T+1 开盘价 − 1) × 1e4`
  - 卖出 `(T+1 开盘价 − 成交价) / T+1 开盘价 × 1e4`
- **执行总成本**（相对信号日收盘，含隔夜跳空）：这部分回测**已经**吃掉了
  （回测按 T+1 开盘成交），所以它不算"缺失"，只是给你一个总成本的感觉。
- **年化换算**：`单笔滑点(bp) / 1e4 × 年双边换手`，换手默认读
  `build/runs/main/metrics.json` 的 `turnover_ann_double = 1.514`。

### report 会输出什么

用 32 笔合成数据演示（μ=16bp、σ=35bp）：

```
实测滑点（4 个交易日，32 笔已成交）
  均值          +0.22 bp
  中位          +3.25 bp
  标准差        29.14 bp
  95% CI 均值 [-9.74, +9.98] bp   （n=32，bootstrap 10000）
  金额加权      +0.30 bp

反推年化成本（年双边换手 1.514x）
        假设滑点        年化成本      vs 40bp 假设
        0.2bp      0.003%         +0.602pp
       40.0bp      0.606%         -0.000pp
  → 实测均值 0.2bp vs 配置 40bp：偏高（可上调收益）
     若把 SLIPPAGE_BP 改成实测值：年化收益 +0.602pp、Sharpe +0.0581
```

**`n < 20` 会打印警告并拒绝给结论。** 单笔滑点噪声可达 ±50bp，
没有 20 笔以上的均值，看到的全是噪声。这条是刻意的：宁可让人多等一个月，也别拍第二个数。

## 3. 测试（`tests/test_fill_log.py`，10 例）

钉住三件事，都是为了防"看起来能跑、其实口径错了"：

1. **符号**：买入成交价高于开盘 = 正滑点；卖出成交价低于开盘 = 正滑点。
   买卖方向写反了，汇总均值还是"合理"的数，发现不了。
2. **年化换算的符号**：实测 0bp < 假设 40bp → 成本更低 → **收益上调** +0.606pp。
   第一版这里写反了（输出 −0.602pp），是测试抓出来的。
3. **模板价格必须是真实空间**：逐只核对 `ref_close == 信号里的 price`（±0.01%），
   以及 `plan_shares == 信号 shares`。后复权价混进来会直接被抓。

## 4. 结论

| 问题 | 答案 |
|---|---|
| 40bp 离谱吗？ | 不离谱，但偏高。「必须付」约 8bp，40bp 相当于 2.38 个 tick |
| 真值大概多少？ | **15~25bp**（半价差 + 少量劣化 + 缓冲），日线只能给区间 |
| 值多少钱？ | 40 → 20bp ⇒ 年化成本 −0.30pp、Sharpe −0.029 的纠正（向上） |
| 现在能改配置吗？ | **不能**。没有一笔实测数据，改了就是拍第二个数 |
| 什么时候能改？ | 攒够 20~30 笔（约 4~6 个调仓周，也就是 4~6 个月） |

**下一步只有一个动作**：每个调仓日花两分钟填 `journal/fills/fills_YYYY-MM-DD.csv` 的两列。
这件事没有任何技术难度，唯一的风险是忘掉。
